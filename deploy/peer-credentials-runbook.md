# Peer credential providers

`mwi` and `superserve` are explicit credential providers. Both publish the same
validated `/etc/superserve/peer/current/{tls.crt,tls.key,ca.crt}` contract. TLS 1.3,
mutual authentication, exact existing SPIFFE URI authorization, routing and the
wire protocol are unchanged. There is no automatic provider switch or plaintext
fallback. Distinct host keys/certificates use the existing shared cell identity;
this does not introduce host-specific SPIFFE identities.

Superserve is an alternative credential source, not a disposable certificate
format. The current implementation supports **operator-driven staging issuance
and installation**, not unattended production operation. MWI remains available
once the Compute platform issue is resolved. Fresh staging VMs still have empty
managed credential directories despite enabled control-plane identity fields;
creation timing, attestation ID, guest settings and agent startup ordering were
ruled out. The available GCP support plan also prevents opening a Compute support
case in production. Do not assume a prompt platform fix.

## Custody and authorization

Use a dedicated CAS pool with a managed, non-exportable KMS signing key. No CA
private key is generated by these scripts, exported, or installed on a VMD.
Only the issuer service account receives `privateca.certificates.create` on this
pool (for example via `roles/privateca.certificateRequester`). VMD accounts must
not have that permission or issuer impersonation. Keep the existing MWI pool and
its distinct permissions separate. Audit inherited IAM as well as pool bindings.

The operator helper impersonates that issuer using the operator's authenticated
gcloud session. Grant operators narrowly scoped impersonation separately from
host runtime IAM. This is not host authentication for a network issuance API:
it is the explicitly authorized manual staging bridge. The reviewed policy maps
host names to expected service-account principals, and the helper compares the
live instance account before preparation, issuance and installation. Do not run
admission or VM replacement concurrently with these operations.

The request's signature proves key possession. The issuer uses only the CSR's
public key; its own policy supplies the exact SPIFFE URI, CN, non-CA constraint,
client/server usages and lifetime. CSR subject and extensions are ignored.
Leaf keys are generated on the host and remain root-owned mode 0600. Local
operator artifacts contain only CSRs, certificates and request metadata.

## One-time staging CA setup

These are operator commands, not executed by this change. Have an infrastructure
administrator provision and review the dedicated pool, issuer IAM and key custody
before issuing. Do not reuse a pool with broad inherited issuance grants. The
following creates a managed CAS/KMS CA; it incurs ongoing cloud charges:

```sh
gcloud privateca pools create superserve-peer-staging --project=rayai-dev --location=us-central1 --tier=enterprise
gcloud privateca roots create superserve-peer-staging-root --project=rayai-dev --location=us-central1 --pool=superserve-peer-staging --subject='CN=Superserve staging peer CA' --key-algorithm=ec-p256-sha256 --max-chain-length=0 --key-usages=cert_sign,crl_sign --extended-key-usages=server_auth,client_auth --validity=P5Y --auto-enable
```

Use the same CA for subsequent automated issuance. CA rollover, expiry monitoring
and deletion protection must be represented in reviewed infrastructure before
production. Do not delete/recreate the CA on each leaf renewal.

Create `.peer-credentials/policy.json` from this shape, replacing the issuer and
host account values with reviewed actual principals. The helper rejects live
account mismatches. Never derive the authorized list automatically from whichever
principal happens to be running on a host:

```json
{
  "ca_pool": "projects/rayai-dev/locations/us-central1/caPools/superserve-peer-staging",
  "issuer_service_account": "REVIEWED_ISSUER@rayai-dev.iam.gserviceaccount.com",
  "spiffe_uri": "spiffe://vmd-peer-staging-usc1.global.669325949364.workload.id.goog/ns/vmd/sa/vmd-peer-proxy",
  "hosts": {
    "superserve-vmd-staging": {"service_account": "REVIEWED_HOST1_ACCOUNT"},
    "superserve-vmd-staging-2": {"service_account": "vmd-runtime-staging-usc1@rayai-dev.iam.gserviceaccount.com"}
  }
}
```

An optional `credential_policy` object sets `leaf_lifetime_seconds` (2592000),
`renew_before_seconds` (1296000), `warn_before_seconds` (864000), and
`critical_before_seconds` (259200). These parenthesized defaults mean 30-day
leaves, renewal due at 15 days remaining, warning at 10 days, critical at 3 days.
The root-owned host `identity.json` must contain the same policy when customized;
the installer refuses a policy mismatch. Preserve its other infrastructure fields.
No policy file or certificate artifact belongs in Git.

## Generate requests, issue and install

From the repository root, after CA/IAM setup and policy review:

```sh
for host in superserve-vmd-staging superserve-vmd-staging-2; do
  python3 deploy/peer-cas.py prepare --policy .peer-credentials/policy.json --host "$host" --directory ".peer-credentials/$host"
  python3 deploy/peer-cas.py issue --policy .peer-credentials/policy.json --host "$host" --directory ".peer-credentials/$host"
  python3 deploy/peer-cas.py install --policy .peer-credentials/policy.json --host "$host" --directory ".peer-credentials/$host"
done
```

Preparation creates the key and CSR through IAP SSH. Issuance sends the verified
public key to CAS using the issuer's policy. Installation sends public material
and the publisher through IAP SCP; it never transfers the CA key or host key.
The request UUID is persisted for idempotent CAS retry. Reuse the directory for
an uncertain issuance result; for a new renewal use a fresh directory/UUID.
CAS guarantees request deduplication for at least 60 minutes. Outside that window,
inspect the certificate ID before retrying an uncertain issuance.

Installation checks validity dates, at least one hour remaining, configured
maximum lifetime, key match, CA chain for both server and client usage, and exact
URI SAN. It validates a complete candidate before an atomic `current` symlink
swap. Failed validation preserves the prior generation. Initial service setup or
status-reporting failure after publication is visible and retryable; it does not
roll back a good publication. The provider selection is stored with the generation
and changes atomically with it. The installer stops the prior credential timer/service before publication to
prevent an MWI refresh racing the provider switch. A failed install can leave
that timer stopped; fix the reported failure and rerun installation.
Timer runs on Superserve only validate/report the
installed generation; they do not issue certificates or fall back to MWI.

For Host 2, export a fresh Terraform bootstrap artifact and finish the guarded
runtime preparation using the already installed Superserve bundle. If you
customized `credential_policy`, copy that reviewed object into `host2.json` before
bootstrap so it is preserved alongside the fresh Terraform identity fields:

```sh
terraform -chdir=infra/envs/staging/us-central1 output -json host2_peer_bootstrap > .peer-credentials/host2.json
python3 deploy/bootstrap-host2.py --provider superserve .peer-credentials/host2.json
```

This leaves VMD stopped for the normal controlled deployment and retains the
standby/non-ready label. A previous failed bootstrap guard is removed only after
successful validation. This operation does not admit the host. Do not rerun normal
MWI bootstrap expecting an automatic downgrade.

## Loading and verifying credentials

**Publication is not runtime reload.** The current proxy is a systemd DynamicUser
service with `LoadCredential` copies populated at service startup. Outbound peer
connections load from those copies when dialing; inbound TLS configuration is
constructed at listener startup. Neither observes a new published generation by
file replacement alone. Superserve publication therefore reports
`proxy_reload_required=true` and does not restart the proxy. The pre-existing MWI
publisher's proxy-restart behavior is retained for compatibility.

For staging, perform the existing controlled proxy deployment/restart on each
host after installation, using the existing listener/routing rollout discipline.
That operation can interrupt proxy streams; schedule it explicitly. Credential
installation does not change listener topology or enable routing. Once the
private peer listeners are deployed on port 5009, verify both directions:

```sh
for host in superserve-vmd-staging superserve-vmd-staging-2; do
  python3 deploy/peer-cas.py verify --policy .peer-credentials/policy.json --host "$host" --directory ".peer-credentials/$host"
done
python3 deploy/bootstrap-host2.py --provider superserve --verify .peer-credentials/host2.json
go test ./internal/proxy -run 'TestPeer(TLS|ClientRejects|IngressRejects|IngressAuthorized)' -count=1
```

The IAP verifier presents the host's current certificate to the other private
listener, validates its CA and exact SPIFFE URI, requires TLS 1.3 and HTTP/2, and
reads a SETTINGS frame so server rejection of client authentication cannot be
mistaken for success. It also compares the served leaf fingerprint with the
other host's installed certificate to detect an outstanding reload. Both commands must pass; a disabled/missing listener fails.
The focused runtime tests cover wrong identity, wrong CA, missing client
certificate and plaintext rejection without introducing probe identities into
live trust. These tests complement, not replace, both live verification commands.

## Visibility and expiration response

`vmd-peer-credentials.timer` checks every minute. The journal and root-only
`/etc/superserve/peer/status.json` report provider, expiration, remaining seconds,
last successful installation, failures, last failure time, renewal due and reload
required. `--check` validates the current generation, including not-before and
expiration. Expired credentials fail checks and new mutually authenticated TLS
handshakes. Already authenticated streams are not terminated at certificate expiry.

Wire warning/critical status and stale `checked_at` (more than five minutes) into
the deployed monitoring system before production. Alert on repeated failures
before expiration, not just expired certificates. This patch provides status and
journal events, **not a deployed alert policy**. For manual staging, inspect:

```sh
gcloud compute ssh superserve-vmd-staging-2 --project=rayai-dev --zone=us-central1-a --tunnel-through-iap --command='sudo cat /etc/superserve/peer/status.json; sudo journalctl -u vmd-peer-credentials.service --since="1 hour ago" --no-pager'
```

At warning: inspect issuer IAM, CAS availability/CA expiry, and failed issuance
request ID; renew using a fresh request directory while the current leaf remains
valid. At critical: escalate and arrange a controlled reload before expiry.
Never remove authentication or install an unvalidated bundle to recover service.
No indefinite retry loop is used. Installation retains old generations for two
days; unneeded host request directories and local public artifacts may be removed
after successful installation and verification. Retain active trust roots.

## Independently reviewable production follow-ups

1. **Authenticated issuer and renewal client.** Deploy a private authenticated
   endpoint accepting host-generated CSRs. Validate token signature, issuer,
   audience, expiry and immutable service-account subject against an explicit
   server-owned allowlist. Do not authorize from a claimed email or request field.
   Shared application service accounts must be replaced with dedicated VMD
   principals before network issuance is enabled. Map that principal to cell identity and policy server-side. Only the issuer
   receives issuance IAM, with no host/issuer key export or static SA keys.
   A request contains CSR and idempotency UUID; the response contains leaf and
   chain, never a private key. The consumer must pin approved trust roots outside
   the response, validate the response against the pending local key and policy,
   and publish atomically. CA changes require explicit trust-rollover authorization.
   Add bounded retries/backoff, jitter, per-principal rate limits, audit logging,
   revocation policy, key/CSR algorithm limits and replay/idempotency storage.
2. **Live rotation.** Provide secure delivery of updated material to the
   unprivileged proxy, atomically load matching cert/key/trust generations, and
   make new inbound/outbound TLS handshakes use them. Keep existing authenticated
   streams alive; do not kill streams merely at expiry. Test successful rotation
   during active streams, bad-generation retention, expired new-handshake failure,
   and provider/trust transition. Systemd credential snapshots plus periodic
   restart are not the production solution. No sandbox lifecycle hot-path I/O.
3. **Operations and infrastructure.** Codify CAS/KMS custody, narrow issuance and
   impersonation IAM, CA lifecycle, renewal schedule and low-cardinality alerts.
   Demonstrate renewal failures and recovery before calling this production-ready.

Returning to MWI is an explicit validated publication, e.g. on each host
`sudo /usr/local/sbin/refresh-peer-credentials --provider mwi`, only after managed
files exist. Coordinate trust and runtime reload across both peers first; different
CA roots can otherwise partition them. Failed MWI publication leaves Superserve
selected. Remove obsolete Superserve request keys and disable its future renewal
client only after the switch is verified. Do not destroy CA trust while any peer
still relies on it.
