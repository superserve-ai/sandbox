# Peer credential providers

`mwi` and `superserve` are explicit credential providers. Both publish the same
validated `/etc/superserve/peer/current/{tls.crt,tls.key,ca.crt}` contract. TLS 1.3,
mutual authentication, exact existing SPIFFE URI authorization, routing and the
wire protocol are unchanged. There is no automatic provider switch or plaintext
fallback. Distinct host keys/certificates use the existing shared cell identity;
this does not introduce host-specific SPIFFE identities.

Superserve is an alternative credential source, not a disposable certificate
format. The current implementation supports **operator-driven staging issuance
and installation**, not unattended production operation. MWI remains available
once the Compute platform issue is resolved. Fresh staging VMs still have empty
managed credential directories despite enabled control-plane identity fields;
creation timing, attestation ID, guest settings and agent startup ordering were
ruled out. The available GCP support plan also prevents opening a Compute support
case in production. Do not assume a prompt platform fix.

## Custody and authorization

Use a dedicated CAS pool with a managed, non-exportable KMS signing key. No CA
private key is generated by these scripts, exported, or installed on a VMD.
Only the issuer service account receives `privateca.certificates.create` on this
pool (for example via `roles/privateca.certificateRequester`). VMD accounts must
not have that permission or issuer impersonation. Keep the existing MWI pool and
its distinct permissions separate. Audit inherited IAM as well as pool bindings.

The operator helper impersonates that issuer using the operator's authenticated
gcloud session. Grant operators narrowly scoped impersonation separately from
host runtime IAM. This is not host authentication for a network issuance API:
it is the explicitly authorized manual staging bridge. The reviewed policy maps
host names to expected service-account principals, and the helper compares the
live instance account before preparation, issuance and installation. Do not run
admission or VM replacement concurrently with these operations.

The request's signature proves key possession. The issuer uses only the CSR's
public key; its own policy supplies the exact SPIFFE URI, CN, non-CA constraint,
client/server usages and lifetime. CSR subject and extensions are ignored.
Leaf keys are generated on the host and remain root-owned mode 0600. Local
operator artifacts contain only CSRs, certificates and request metadata.

## Terraform custody setup

`infra/modules/peer-ca` owns the CAS pool/root, managed KMS signing configuration,
issuer service account, pool issuance IAM and optional operator impersonation.
Staging instantiates it in `infra/envs/staging/us-central1/peer_ca.tf`; production
must instantiate distinct pools/roots for its environment/cell trust boundaries.
The existing MWI pool remains separate and unchanged. Private CA and IAM APIs
must already be enabled by the environment (staging's MWI setup does this).

The pool permits only config-based leaf issuance, limits lifetime, and enforces
one exact existing peer URI SAN and the `vmd-peer-proxy` CN. CAS creates the
non-exportable KMS signing key from `EC_P256_SHA256`; Terraform stores algorithm
and resource metadata, never key bytes. The root permits no subordinate CAs.
Pool, CA and issuer have `prevent_destroy`; the CA also has API deletion
protection. CA/key replacement requires deliberate reviewed lifecycle changes;
removing a module from configuration also removes its Terraform lifecycle guard,
so API deletion protection and restricted administrative IAM remain essential.
No service-account keys, leaf certificates, CSRs or runtime generations are in
Terraform. The root CA's public certificate is infrastructure metadata.

`peer_ca_operator_members` defaults to an empty set: no operator access is
inferred. To enable the manual bridge, set explicitly reviewed `user:`/`group:`
principals in the environment's Terraform inputs. The grant is
`roles/iam.serviceAccountTokenCreator` on this issuer only. Runtime service-account
principals are rejected. This is privileged issuance access through impersonation;
remove a principal from the input to revoke the managed grant. Both the pool role
binding and a configured operator role binding are authoritative for their role;
do not manage the same role with separate member resources. Audit inherited IAM.

Review an ordinary plan before any operator apply. No apply is performed by this
code change. If a matching CA/pool/account was already created manually, import
those resources at the module addresses before planning; never destroy/recreate
an active CA to resolve a name conflict. Read-only validation and mocked tests:

```sh
terraform -chdir=infra/envs/staging/us-central1 init
terraform -chdir=infra/envs/staging/us-central1 validate
terraform -chdir=infra/envs/staging/us-central1 plan
terraform -chdir=infra/modules/peer-ca init
terraform -chdir=infra/modules/peer-ca test
```

After the reviewed infrastructure has been applied, export the non-secret policy:

```sh
# Issuance is a runtime/operator operation, never a Terraform leaf resource.
```

The staging-only `peer-cas.py` recipe remains on the migration branch. For
production, use the reviewed authenticated issuer with host-generated CSRs;
the issuer owns SPIFFE identity and policy and alone holds CAS issuance rights.
Do not deploy an ad-hoc staging host allowlist as an automated production issuer.
The consumer installs supplied bundles using `refresh-peer-credentials --provider
superserve --cert ... --key ... --ca ...`; publication is validated and atomic.
No production-ready automated renewal service is included in this consumer PR.

Credential files loaded with systemd LoadCredential are snapshots at service
start. File publication alone does not provide live inbound TLS reload; outbound
reload depends on the connection manager. Production rotation must preserve
already authenticated streams and load fresh credentials for new connections;
treat that integration and automated renewal as explicit follow-up requirements.

## Visibility and expiration response

`vmd-peer-credentials.timer` checks every minute. The journal and root-only
`/etc/superserve/peer/status.json` report provider, expiration, remaining seconds,
last successful installation, failures, last failure time, renewal due and reload
required. `--check` validates the current generation, including not-before and
expiration. Expired credentials fail checks and new mutually authenticated TLS
handshakes. Already authenticated streams are not terminated at certificate expiry.

Wire warning/critical status and stale `checked_at` (more than five minutes) into
the deployed monitoring system before production. Alert on repeated failures
before expiration, not just expired certificates. This patch provides status and
journal events, **not a deployed alert policy**. For manual staging, inspect:

```sh
gcloud compute ssh superserve-vmd-staging-2 --project=rayai-dev --zone=us-central1-a --tunnel-through-iap --command='sudo cat /etc/superserve/peer/status.json; sudo journalctl -u vmd-peer-credentials.service --since="1 hour ago" --no-pager'
```

At warning: inspect issuer IAM, CAS availability/CA expiry, and failed issuance
request ID; renew using a fresh request directory while the current leaf remains
valid. At critical: escalate and arrange a controlled reload before expiry.
Never remove authentication or install an unvalidated bundle to recover service.
No indefinite retry loop is used. Installation retains old generations for two
days; unneeded host request directories and local public artifacts may be removed
after successful installation and verification. Retain active trust roots.

## Independently reviewable production follow-ups

1. **Authenticated issuer and renewal client.** Deploy a private authenticated
   endpoint accepting host-generated CSRs. Validate token signature, issuer,
   audience, expiry and immutable service-account subject against an explicit
   server-owned allowlist. Do not authorize from a claimed email or request field.
   Shared application service accounts must be replaced with dedicated VMD
   principals before network issuance is enabled. Map that principal to cell identity and policy server-side. Only the issuer
   receives issuance IAM, with no host/issuer key export or static SA keys.
   A request contains CSR and idempotency UUID; the response contains leaf and
   chain, never a private key. The consumer must pin approved trust roots outside
   the response, validate the response against the pending local key and policy,
   and publish atomically. CA changes require explicit trust-rollover authorization.
   Add bounded retries/backoff, jitter, per-principal rate limits, audit logging,
   revocation policy, key/CSR algorithm limits and replay/idempotency storage.
2. **Live rotation.** Provide secure delivery of updated material to the
   unprivileged proxy, atomically load matching cert/key/trust generations, and
   make new inbound/outbound TLS handshakes use them. Keep existing authenticated
   streams alive; do not kill streams merely at expiry. Test successful rotation
   during active streams, bad-generation retention, expired new-handshake failure,
   and provider/trust transition. Systemd credential snapshots plus periodic
   restart are not the production solution. No sandbox lifecycle hot-path I/O.
3. **Operations and production infrastructure.** Apply the reviewed custody module
   with distinct production trust domains, audit inherited IAM, and add CA lifecycle
   monitoring, renewal schedules and low-cardinality alerts.
   Demonstrate renewal failures and recovery before calling this production-ready.

Returning to MWI is an explicit validated publication, e.g. on each host
`sudo /usr/local/sbin/refresh-peer-credentials --provider mwi`, only after managed
files exist. Coordinate trust and runtime reload across both peers first; different
CA roots can otherwise partition them. Failed MWI publication leaves Superserve
selected. Remove obsolete Superserve request keys and disable its future renewal
client only after the switch is verified. Do not destroy CA trust while any peer
still relies on it.
